일의 단위가 바뀌면 질문도 바뀐다 — 화면 하나에서 에픽 하나로, Flutter 1년 3개월

들어가며: PR 제목이 티켓 번호로 시작하던 때

저는 Flutter 로 웰니스 앱을 만들고, 앱이 부르는 서버(Django·FastAPI)도 함께 맡고 있어요. 개발 경력은 3년쯤 됐고, 그중 이 회사에서 Flutter 로 일한 시간이 1년 3개월이에요. 2025년 7월 말에 입사해 다른 프로젝트를 먼저 맡았고, 지금의 앱 저장소에는 10월 말부터 커밋했어요. 아래 분기 기록은 이 앱의 2025년 11월 중순부터 1년 치를 다뤄요.

최근에 지난 1년 동안 제가 올린 PR 목록을 처음부터 끝까지 펼쳐 봤어요. 첫 분기의 PR 제목은 거의 다 이런 모양이었어요.

text
feat: <티켓 번호> onboarding primary goal
feat: <티켓 번호> onboarding loading
feat: <티켓 번호> progress calendar
feat: <티켓 번호> chatting UI

티켓 하나가 화면 하나였고, 화면 하나가 PR 하나였어요. 마지막 분기의 PR 제목은 이렇게 바뀌어 있었어요.

text
feat(social): 소셜 DB 스키마와 마이그레이션 추가
feat(social): 게시물·댓글 번역 API — 요청 시 번역 + 캐시
feat(running-coach): 러닝 시작 안내와 구간 평균 심박을 보낸다
feat(watch): Apple Watch 컴플리케이션 10종과 탭 상세 화면

같은 사람이 올린 PR 인데, 앞의 것은 화면 이름이고 뒤의 것은 한 기능을 이루는 여러 층 중 하나의 이름이에요. 이 글에서는 여러 층(앱, 서버, 실시간·AI 서버, 네이티브)에 걸친 기능 묶음 하나를 에픽이라고 부를게요.

이 글은 그동안 쓴 기술 글들을 닫는 회고예요. 각 글은 한 가지 문제를 깊게 다뤘다면, 이 글은 그 문제들이 언제, 어떤 순서로 찾아왔는지를 이어 붙여요. 분기마다 대표 사건 하나와 그때 배운 것을 적고, 마지막에 앞으로 할 일을 적었어요.

처음에 무엇을 기대했는지도 적어 두고 싶어요. 입사할 무렵 저는 이 일에서 앱 개발자로서의 커리어를 기대했어요.

Flutter 로 화면을 만드는 일에서 범위를 넓혀 가고 있는 분, 그리고 AI 코딩 에이전트와 일하는 속도가 붙기 시작한 분께 참고가 될 거예요.

첫 분기: 화면 하나를 끝내는 게 일의 단위였다

첫 분기(2025년 11월 중순~2026년 2월 중순)에 main 에 들어간 제 PR 은 전부 앱 저장소에 있었어요. 서버 저장소에는 PR 이 하나도 없었어요. 온보딩 화면부터 시작해서 기록 화면, 홈, 채팅 UI, 프로필 순서로 티켓이 오면 그 화면을 만들었어요.

이 시기를 대표하는 장면으로 1월 말의 탭바 작업 하나를 고를게요. 하단 탭바를 유리처럼 보이게 만드는 티켓이었어요. 저는 Flutter 쪽 유리 효과 패키지를 써서, 선택된 탭 뒤에 반투명 둥근 모양이 미끄러지는 탭바를 Flutter 위젯으로 그렸어요. 화면 안에서 끝나는 일이었고, 화면 안에서 끝냈어요.

이 탭바는 아홉 달 뒤에 다른 모습으로 돌아와요. 그 이야기는 마지막 분기에서 할게요.

이 분기에 AI 코딩 에이전트와 함께 코드를 쓰기 시작했어요. 앞 글에 적었듯 1월부터 코드 대부분을 Claude Code 같은 에이전트와 함께 썼어요. 다만 커밋에 AI 공동 작성 표시(Co-Authored-By)가 처음 붙은 건 3월이라, 이 시기 기록에는 그 흔적이 남아 있지 않아요.

이 분기에 배운 건 Flutter 프레임워크에 대한 이해였어요.

둘째 분기: 서버 저장소를 처음 열었다

둘째 분기(2월 중순~5월 중순)에도 대부분의 PR 은 화면이었어요. 기록 상세 화면, 챌린지 화면, 팀 메인 화면처럼요. 달라진 건 4월에 처음으로 서버 저장소에 PR 을 올렸다는 거예요. 첫 서버 PR 은 기록 보상 코인을 고치는 작은 수정이었어요.

곧이어 친구 초대 기능을 맡았어요. 초대 링크로 앱을 설치한 사람을 첫 실행 때 초대자와 이어 주는 기능이에요. 앱 안에서는 풀 수 없는 문제였어요. 설치를 거치면 링크 정보가 사라지니까요. 결국 매칭을 서버에서 직접 하기로 했고, 그 판단과 대가는 디퍼드 딥링크 글에 따로 적었어요.

이 일에서 처음으로 “화면이 원하는 데이터를 서버가 어떻게 만들어 주는가”를 제가 정해야 하는 자리에 섰어요. 그전까지 API 는 받아서 쓰는 것이었어요. 서버 작업을 맡게 된 건 AI 가 발전하면서 자연스럽게 백엔드도 같이 하게 됐기 때문이에요.

3월에는 커밋에 AI 공동 작성 표시가 붙기 시작했고, 4월에는 제 커밋의 약 3할에 그 표시가 붙었어요. (표시 없이 AI 를 쓴 커밋도 있어서 실제보다 낮게 잡힌 값이에요.)

이 분기에 배운 건 Django 와 FastAPI 에 대한 이해였어요.

셋째 분기: 에이전트에게 일을 나눠 주는 법을 만들었다

셋째 분기(5월 중순~8월 중순)에 서버 PR 이 앱 PR 에 가까워졌어요. main 에 들어간 Django PR 이 앞 분기 8건에서 87건으로 늘었어요(같은 분기 앱 PR 은 132건). 팀 기능, 인앱 결제와 구독, 배틀패스 유료 전환처럼 앱과 서버를 같이 바꿔야 하는 기능을 연달아 맡았기 때문이에요.

이 분기의 대표 사건으로 6월에 AI 에이전트용 규칙 문서를 처음 정비한 일을 고를게요. 정비를 시작한 계기는 솔직히 기억에 남아 있지 않아요. 하나로 뭉쳐 있던 규칙 파일을 규칙과 아키텍처 지도로 나누고, 설계 결정 기록(ADR)과 인수인계 문서 자리를 만들었어요. 같은 시기에 기획·구현·리뷰·QA 를 나눠 맡는 에이전트와, 반복 리뷰 항목을 하나씩 맡는 명령들을 만들었어요.

직접 만든 도구 중에는 스토어 인앱 상품 가격을 등록하는 도구와 스킬도 있었어요. 나라별 가격을 콘솔에서 손으로 넣던 일을 스크립트로 옮긴 거예요. 이후 스토어 스크린샷 업로드, 언어별 메타데이터 추출, 리뷰 봇 대신 PR 을 리뷰하는 스킬까지, 1년 동안 직접 만든 에이전트·명령·스킬이 약 24개가 됐어요.

AI 공동 작성 표시가 붙은 커밋 비율은 이 분기에 가장 높았어요. 6~8월에는 달마다 제 커밋의 약 65~73% 였어요. 이 비율은 표시를 붙이는 습관에 따라 달라지는 값이라 “AI 가 코드의 7할을 썼다”로 읽으면 안 돼요. 다만 에이전트에게 기획·구현·리뷰처럼 역할을 나눠 맡기기 시작한 시기인 건 기록으로 확인돼요.

규칙 문서는 이후 계속 자라서, 10월에는 예산을 16바이트 남기고 꽉 찼어요. 그 문서를 어떻게 예산 안에 두었는지는 에이전트 규칙 글에 있어요.

넷째 분기: 에픽 하나를 층마다 나눠 설계했다

넷째 분기(8월 중순~11월 중순)에는 PR 제목 맨 앞이 티켓 번호에서 기능 이름으로 바뀌었어요. 앱 PR 161건, Django PR 143건, FastAPI PR 13건이 main 에 들어갔어요. 첫 분기에 앱 저장소 하나였던 범위가 앱·서버·실시간/AI 서버·인프라 네 층이 됐고, 플랫폼도 iOS·Android 두 개에서 iOS·Android·watchOS·iOS 홈 위젯·Wear OS 다섯 개가 됐어요.

이 분기는 에픽이 겹쳐서 지나갔어요. 순서대로 짧게 적으면 이래요.

8월에는 온보딩 설문이 답마다 전체 화면 로딩을 띄우던 걸 고쳤어요. 앱은 답변을 백그라운드 직렬 큐로 보내고, 서버는 “이 답이 다음 문항을 바꾸는지” 신호를 응답에 더했어요. 로딩이 23번에서 2번으로 줄었어요(설문 저장 큐 글).

9월에는 루틴 Live Activity 13종과 홈 위젯 10종을 만들었어요. 앱이 잠든 동안 배너를 바꿀 주체가 없다는 걸 QA 보고로 알게 됐고, 서버가 push 로 배너를 돌리는 구조에 도착하기까지 첫 설계가 실기기에서 두 번 무너졌어요(Live Activity 글).

10월에는 러닝 기능을 폰·Apple Watch·Wear OS 에 붙이고, FastAPI 쪽에 구간마다 LLM 으로 코칭 문장을 만들고 TTS 로 읽어 주는 API 를 붙였어요. 같은 달 말에는 소셜 기능을 맡았어요. 서버 쪽은 테이블 14개짜리 스키마부터 피드·댓글·DM·알림·신고·번역 API, 1차 자동 검사와 AI 2차 검토로 이어지는 검열까지 만들었고, DM 실시간 신호는 FastAPI 로 보냈어요. 화면별 QA 를 나눈 것 말고는 앱과 서버를 혼자 설계하고 만들었어요.

11월에는 코인을 걸고 참여하는 챌린지를 사용자 챌린지와 상시 운영 공식 챌린지로 나눠 만들었어요. 판정과 정산은 서버가 갖고, 앱은 서버가 계산한 금액을 보여 주는 쪽으로 나눴어요.

이 분기의 대표 사건 하나를 고르자면 소셜 에픽이에요. 소셜에서는 화면 기획과 별도로 앱과 서버 사이의 계약 문서를 두었어요. 앱은 그 계약에 맞춘 가짜(mock) 데이터로 화면을 먼저 만들고, 서버 API 가 머지될 때마다 의존성 주입 한 곳에서 실제 구현으로 갈아 끼웠어요. 서버를 기다리지 않고 두 층을 나란히 진행할 수 있었던 건 이 계약 덕분이었어요.

이 분기에 배운 건 이거예요. 에픽에서 어려운 건 각 층의 코드가 아니라, 층과 층 사이에서 누가 무엇을 소유하는지 정하는 일이었어요. 금액은 누가 계산하는지, 배너 문구는 서버가 만드는지 위젯이 만드는지, 구버전 앱은 새 필드가 없을 때 어떻게 보이는지 같은 것들이요. 이걸 먼저 정하면 나머지는 각 층 안의 문제가 됐어요.

빠르게 머지한 대가는 11월에 한꺼번에 왔다

넷째 분기의 속도에는 그림자가 있었어요.

PR 을 만들고 머지하기까지 걸린 시간의 중앙값은 첫 분기 18.5시간에서 넷째 분기 0.8시간이 됐어요. 이 숫자는 그대로 “빨라졌다”로 읽으면 안 돼요. 첫 분기에는 develop 브랜치를 거쳐 main 에 반영했고, 넷째 분기에는 에픽 브랜치에 제가 직접 머지하는 일이 많았어요. 프로세스가 바뀐 몫이 섞여 있어요. 그리고 바로 그 섞인 몫이 문제였어요. 리뷰 없이 머지한 PR 이 많았다는 뜻이기도 하니까요.

11월에 그 대가가 한꺼번에 보였어요.

코드를 하루 잡고 직접 읽어 보니, BLoC 에서 이벤트가 겹칠 때의 처리를 약 270곳이 저마다 다른 방법으로 풀고 있었어요. 이걸 다시 AI 와 함께 하나의 기준으로 정리한 이야기가 BLoC 글이에요.

같은 달에 iOS 크래시가 21개 빌드 동안 0건으로 집계되고 있었다는 걸 알았어요. CocoaPods 에서 Swift Package Manager 로 옮기면서 조용히 실패하기 시작한 빌드 단계 하나 때문이었어요(Crashlytics 글). 그 전환 자체를 어떻게 했는지는 SPM 전환 글에 따로 적었어요.

리뷰를 사람 눈에만 기대지 않는 장치도 이때 만들었어요. 공용 위젯에 접근성 노드와 QA 용 식별자를 붙여서, 실기기 QA 를 스크립트가 화면 요소를 찾아 누르는 방식으로 돌릴 수 있게 했어요(실기기 QA 글).

그리고 1월의 탭바가 돌아왔어요. iOS 26 에서는 Flutter 로 그린 유리 대신, 시스템 탭바를 플랫폼 뷰로 그대로 띄우는 방식으로 바꿨어요(Liquid Glass 탭바 글). 1월에는 화면 안의 위젯 문제였던 것이, 11월에는 Flutter 와 네이티브 중 어느 쪽이 그릴지 정하는 문제가 돼 있었어요.

BLoC 글과 Crashlytics 글을 쓰면서 공통점을 하나 찾았어요. 둘 다 “잘 돌아가는 것처럼 보이던 이유를 몰랐던 것”이에요. 이벤트 겹침이 드물어서 코드가 잘 돌아갔고, CocoaPods 가 대신 해 주던 일 덕분에 크래시가 잘 올라갔어요. 속도가 빨라질수록 그 이유를 확인하는 일은 먼저 빠졌어요.

앞으로 할 일

기록에 남아 있던 후보 세 가지를 그대로 다음 계획으로 삼을게요. 워치 러닝 앱과 위젯, 소셜 기능은 실기기 확인이 아직 남아 있어서 이걸 먼저 끝낼 거예요. 에이전트 규칙 문서는 지금 사람이 손으로 덜어 내고 있어서, 넘칠 때를 도구가 먼저 알려 주게 만들 거예요. BLoC 정리처럼 한 번 정한 기준을 리뷰하는 쪽도 같이 읽게 하는 일도 이어 갈 거예요.

더 길게 보면 다양한 개발을 해 보고 싶어요. 지루하고 가장 오래 걸리는 코딩을 AI 가 해 주니까, 여러 가지 개발을 해 볼 기회가 앞으로 많을 거라고 생각해요.

마치며: 단위가 바뀌면 질문도 바뀐다

1년 전 PR 제목은 화면 이름이었고, 지금은 층의 이름이에요. 돌아보면 바뀐 건 다루는 기술의 개수보다 스스로 던지는 질문이었어요. 첫 분기의 질문은 “이 화면을 시안대로 만들 수 있나”였어요. 지금은 “이 데이터는 어느 층이 소유하나”, “앱이 꺼져 있을 때는 누가 이걸 바꾸나”, “구버전 앱에서는 어떻게 보이나”를 먼저 물어요.

처음에 기대한 건 앱 개발자로서의 커리어였어요. 1년이 지난 지금, 경력은 나름 잘 쌓은 것 같아요. 앱, 서버, 기획, 디자인까지 다양하게 경험했고, 그 과정에서 많은 것을 배웠어요.

일의 단위를 키우는 건 화면을 더 많이 만드는 게 아니라, 화면 바깥의 질문을 먼저 던지는 일입니다.

그리고 속도에 대해 하나를 덧붙이고 싶어요. AI 와 일하면서 머지는 하루에서 한 시간 안으로 줄었어요. 줄어든 시간에서 가장 먼저 빠진 건 “왜 이게 돌아가지?”를 확인하는 시간이었어요. 그 비용은 몇 달 뒤 한꺼번에 돌아왔어요.

화면 단위에서 범위를 넓혀 가고 있다면, 이렇게 물어보세요.

  1. 지금 만드는 화면의 데이터는 어느 층이 소유하나? 앱이 계산하고 있는 값 중 서버가 가져야 할 게 있지 않나?
  2. 앱이 꺼져 있거나 구버전일 때, 이 기능은 어떻게 보이나?
  3. 최근 한 달 동안 머지한 코드 중, 왜 잘 돌아가는지 설명할 수 있는 건 몇 개인가?

마지막으로 1년 동안 함께 일한 동료들께 고마워요. 같이 일할 수 있어서 좋았고, 저에게는 많이 배울 수 있는 기회였던 것 같아요.
